# 启动时默认解锁全部装备

## Intent

服务启动时自动在实际运行数据目录中创建 `unlock_all_equipment.txt`，复用已有装备权限下发机制。源码、Docker 和 Windows 打包版本都经过 `zwift_offline.py` 的公共初始化逻辑。

## Tasks & Acceptance

- [x] `zwift_offline.py`：确认 `storage` 已创建后，补建全部装备解锁标记；已有文件不覆盖，权限接口继续读取同一个路径。
- [x] `README.md`：将手工创建说明更新为默认开启，并说明缺失文件会在下次启动时重建。
- [x] 使用临时数据目录验证首次创建、再次启动、已有非空文件及装备权限结果；运行现有测试。
- [x] 检查实际运行的 Windows EXE 和数据目录，为当前服务补建缺失的解锁标记，并通过真实 HTTPS 接口验证权限。
- [x] 交付包含启动默认解锁逻辑的新 EXE，并在独立目录验证正式产物自动创建文件及实际权限响应。

Given 数据目录不存在或没有解锁文件，When 服务初始化，Then 创建数据目录和空解锁文件，后续权限下发包含当前权限表内的全部装备。

Given 解锁文件已存在且包含内容，When 服务再次初始化，Then 文件内容保留并继续解锁全部装备。

Given 解锁文件已被删除，When 服务再次初始化，Then 自动补建文件。

## Boundaries

沿用源码目录或 EXE 同级的 `storage` 路径规则。只修改默认装备配置，不增加等级、经验、成就或新的界面配置。保留工作区其他未提交修改，不修改其他进行中的实现文档。

- 在临时 EXE 运行目录模拟冻结环境，实际导入完整服务模块：首次自动创建 `storage` 和空标记文件；再次初始化保留非空文件内容及修改时间；删除后重新初始化可补建。
- 实际玩家资料 protobuf 响应包含当前权限表全部 2256 项装备使用权限，重复更新不产生重复权限。

本次没有新增与实现重复的持久化测试文件。首次实现只更新源码；后续用户反馈实际游戏未解锁，检查确认运行中的 `dist/zoffline.exe` 归档没有新初始化逻辑，且实际 `dist/storage` 没有解锁标记。

## Windows 运行验证与交付

在保持当前游戏和服务运行的情况下，先读取当前服务资料，确认装备 USE 权限为 0；在实际 `dist/storage` 创建空 `unlock_all_equipment.txt` 后，再次请求 `/api/profiles/me` 和 `/api/profiles/me/entitlements`，两者均返回全部 2256 项有效装备权限。玩家 ID、等级、经验和 Drops 未改变。

新 EXE 使用现有固定依赖、`standalone.spec` 和独立构建目录生成，交付至 `dist/zoffline-unlocked.exe`，继续使用同目录已有 `storage`。客户端需要重新登录以重新获取装备权限。

- 完整现有测试：191 项通过；`pip check` 通过。

- 检查 EXE 归档，包含默认装备解锁初始化及权限表，不包含运行时 `storage` 或玩家资料。
